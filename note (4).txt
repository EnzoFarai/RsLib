# 5. LOCKED TECHNICAL ARCHITECTURE AND DESIGN DECISIONS

These decisions were developed through nine planning and review rounds.

Treat them as the agreed technical design.

Do not reopen them merely to propose a different architecture. If an actual supplied file conflicts with the design, identify the discrepancy and ask the operator before changing anything.

## 5.1. URL contracts

Personalised lesson URL:

`/read/{course}/{lesson}.html?view={token}`

The parameter is **`view`**, not `annotations`.

Collection URLs:

- `/bookmarks/{username}`
- `/highlights/{username}`
- `/notes/{username}`

These are username-based collection routes. They do not use a collection share token.

There are four distinct sharing actions:

1. **Selected text:** shares the clean lesson URL.
2. **Lesson:** shares the clean lesson URL.
3. **Annotated view:** shares the personalised `?view=` URL.
4. **Collection:** shares the username-based collection URL.

Do not merge these into one generic sharing mechanism.

## 5.2. Annotation-view token format

Tokens must use:

- 128 bits of cryptographic randomness.
- Base64URL encoding.
- Exactly 22 characters.
- PostgreSQL `TEXT`, not `UUID`.

Generation is server-side through:

`public._random_token()`

The function uses:

`extensions.gen_random_bytes(16)`

Do not substitute UUIDv4. UUIDv4 has 122 random bits, not the required 128.

## 5.3. Collection visibility

Collection visibility has exactly two values:

- `private`
- `public`

Default:

`private`

There is no `restricted` state.

The CHECK constraint must exclude any other value.

`share_collection()` is the intended mechanism for changing a collection to public.

Re-sharing a collection clears `revoked_at`. It does not rotate a token because collection URLs are username-based.

## 5.4. Annotation-link permissions

`reading_annotation_links` is SELECT-only for `authenticated`.

Authenticated client roles must not receive direct:

- INSERT
- UPDATE
- DELETE

The intended writers are SECURITY DEFINER triggers and RPCs.

`service_role` has privileged database access. Do not confuse service-role privileges with ordinary client permissions.

## 5.5. Annotation-link lifecycle RPCs

Two lifecycle RPCs were added beyond the earlier v8 design.

### `revoke_annotation_link(course_id, lesson_id)`

- Sets `revoked_at = now()`.
- Retains the existing token.
- The old URL must return a revoked status.

### `reshare_annotation_link(course_id, lesson_id)`

- Generates and stores a new token.
- Clears `revoked_at`.
- Returns the new token.
- The previous token remains invalid.
- Raises if no link exists.

Both are designed as SECURITY DEFINER functions scoped to `auth.uid()`.

Recorded grants:

- Revoke from `PUBLIC` and `anon`.
- Grant to `authenticated` and `service_role`.

**Service-role caveat:** These lifecycle RPCs require `auth.uid()`. A service-role invocation without a user JWT generally has no authenticated user identity. The grant alone therefore does not establish a usable service-role administration route.

Inspect the actual SQL and document this limitation.

Do not silently change the grants or authentication logic.

## 5.6. New function security

New SECURITY DEFINER functions must use:

`SET search_path = ''`

Schema-qualify references, including:

- `pg_catalog`
- `public`
- `extensions`
- `auth.uid()`

Do not introduce dynamic SQL.

`_random_token()` is intended to be executable only by `service_role`.

Do not grant trigger functions to client roles.

Distinguish direct EXECUTE permissions from the internal invocation of a trigger function by PostgreSQL.

## 5.7. Concurrency behaviour

Use the following accurate description:

- `SELECT ... FOR UPDATE` locks existing rows. It does not lock the absence of a row.
- First-time concurrent inserts rely on the primary key and `INSERT ... ON CONFLICT DO NOTHING`.
- If cleanup holds or deletes an existing link while an insert waits, the insert may recreate the link after cleanup commits.
- Bulk operations involving multiple lessons and different lock orders can deadlock.
- PostgreSQL aborts one competing transaction. The caller must retry the aborted transaction.
- Do not claim deadlocks are impossible.
- Do not claim a deadlock causes data corruption.

The implementation and documentation must reflect these limitations.

## 5.8. CDN dependency

The existing Supabase CDN import remains unchanged.

Do not introduce another CDN or vendor a new dependency.

Document the existing CDN dependency as deferred technical debt.

## 5.10. SQL style and design requirements

The migration design was reviewed against the following requirements:

- `COALESCE` and `NULLIF` are not schema-qualified.
- Real functions are schema-qualified where required.
- Examples include `pg_catalog.length`, `pg_catalog.now`, `pg_catalog.replace`, `pg_catalog.rtrim`, `pg_catalog.encode`, `pg_catalog.jsonb_agg`, `pg_catalog.jsonb_build_object`, `pg_catalog.jsonb_array_length`, `pg_catalog.gen_random_uuid`, `pg_catalog.pg_options_to_table` and `pg_catalog.pg_get_constraintdef`.

## 10.3.7. Public collection visitor experience

The collection routes are:

- `/bookmarks/{username}`
- `/highlights/{username}`
- `/notes/{username}`

The visibility model is:

- `private`
- `public`

The default is private.

Inspect the supplied material to establish:

- How the collection owner's username is displayed.
- How the collection type is identified.

- Whether visitors can navigate to the original public lesson.
- Which actions are available to visitors.
- Which owner-only controls must be hidden.
- How private collections are handled.
- How unavailable users or collections are handled.
- How empty collections are displayed.

Do not expose private collection contents.

The intended retrieval mechanism is:

`get_collection_by_username(text,text)`

The collection page must respect the returned access status.

Use the agreed uniform `{status:'denied'}` handling.

Do not leak whether a private collection exists through inconsistent client-side messages.

## 10.3.8. Annotation sharing and shared lesson views

The four sharing actions are specified in §5.1:

1. Selected text — clean lesson URL.
2. Lesson — clean lesson URL.
3. Annotated view — personalised `?view={token}` URL.
4. Collection — username-based collection URL.

Inspect the reference demonstrations and existing interface to establish where these actions appear, how users invoke them and what feedback is displayed.

The personalised lesson URL is:

`/read/{course}/{lesson}.html?view={token}`

The parameter must remain `view`.

The annotated-view link allows a visitor to see the permitted shared annotation view without receiving access to the owner's account or private collection-management controls.

Respect the token lifecycle:

- Tokens are generated server-side.
- Revocation invalidates the shared view.
- Re-sharing rotates the token.
- The previous token must not become valid again.
- Revoked links must return the agreed `{status:'revoked'}` state.

Do not implement collection sharing using annotation-view tokens.

## 10.3.9. Persistence and authentication

Across bookmarks, highlights and notes:

- Supabase is canonical for authenticated users.
- LocalStorage is for UI-state caching only.
- Annotation content must not be treated as permanently saved merely because it exists in LocalStorage.
- Confirm successful database writes before showing a saved state.
- Failed writes must show an appropriate failure state.
- Loading and pending states must be distinguishable from successful saves.
- Private data must not be exposed.
- Frontend access must agree with database RLS and RPC permissions.

Inspect actual SQL and frontend calls.

Do not assume that a database function's existence proves that frontend integration is correct.

## 14. Recommended personalised URL architecture

Use the following URL format:

```text
/read/{course}/{lesson}.html?view={unique-identifier}
```

For example, the ordinary reading page is:

```text
/read/g12-life-sciences/introduction-to-nucleic-acids.html
```

A personalised version might be:

```text
/read/g12-life-sciences/introduction-to-nucleic-acids.html?view=Gx9nTQ5AJVr8MZ2L0o-3kA
```

Another learner could have:

```text
/read/g12-life-sciences/introduction-to-nucleic-acids.html?view=Hf6pLQ8sWvN1bR4yTu9mCA
```

These are illustrative identifiers, not hardcoded values.

### Why this format?

Retaining the course and lesson name makes the address readable and easy to understand.

The opaque identifier distinguishes different users' personalised views of the same lesson.

Using a query parameter avoids requiring new server routes for every existing `.html` reading page.

It also preserves the existing lesson hierarchy and canonical HTML files.

Do not use the shorter:

```text
/read/g12-life-sciences/{unique-identifier}
```

as the primary format.

Do not use:

```text
/read/g12-life-sciences/introduction-to-nucleic-acids.html/{unique-identifier}
```

unless the application has deliberately implemented the required server routing.

The preferred implementation for Vulanet's current architecture is:

**`/read/{course}/{lesson}.html?view={unique-identifier}`**

---

## 15. Identifier creation and lifecycle

### Automatic creation

When an authenticated learner opens a reading lesson, Vulanet should automatically identify their personal reading-view record.

If one already exists, reuse it.

If this is their first visit to that lesson, create a new personalised view identifier.

The URL may be updated without a full page reload, provided the correct personalised state has loaded.

Do not generate a different identifier on every refresh.

Do not generate a new identifier whenever a highlight or note is added.

### One identifier per personalised lesson

For a particular learner and lesson, Highlights and Notes must refer to **the same personalised reading view**.

For example, making three highlights and two notes in Introduction to Nucleic Acids must not generate five personalised links or separate links for Notes and Highlights.

All five annotations belong to the same view.

Bookmarks do not require a separate personalised reading identifier.

### Sharing eligibility

The existence of a personalised view identifier does not automatically mean its contents must be publicly accessible.

The identifier may be created on the user's first visit, but sharing permissions must be controlled separately.

For an unannotated lesson, the ordinary canonical lesson URL is the default sharing destination.

Once the learner has saved highlights or notes, the personalised URL can be used for sharing that annotated reading experience, subject to the access rules.

A bookmark alone must not make an annotated share link necessary.

### Stable identifiers

A personalised view identifier should remain unchanged while the learner continues adding, editing or partially deleting annotations from the same lesson.

### Removing every annotation

When the learner deletes **all saved highlights and all saved notes** from a particular lesson:

1. Retire the current personalised sharing identifier.
2. Return the learner to the ordinary clean lesson URL.
3. Ensure the old personalised link cannot expose future annotations.
4. Preserve any independent bookmark record for that lesson.

If the learner later begins another annotation cycle, create a fresh identifier.

If the system automatically creates view records on subsequent authenticated visits, it must still ensure that a retired identifier is never reused.

### Old links

If someone opens an old personalised link after its associated annotations have deliberately been removed, redirect them to the ordinary clean lesson.

For example:

```text
/read/g12-life-sciences/introduction-to-nucleic-acids.html
```

However, distinguish intentional deletion from an access restriction.

If a link was revoked, made private or otherwise access-denied, show an appropriate unavailable or access-denied state.

**Never redirect in a way that circumvents a deliberate privacy restriction.**

Retired identifiers must not suddenly begin displaying new annotations when the owner starts annotating the same lesson again.

## 16. Unique identifier quality and security

Identifiers must be generated using a cryptographically secure random mechanism.

Use at least 128 bits of randomness, encoded in an appropriate URL-safe format such as Base64URL.

The system should enforce uniqueness through the database.

Do not use predictable sequential numbers, usernames, timestamps alone or client-generated insecure random values.

The identifier space should comfortably support very large numbers of personalised views.

Although the identifiers should be difficult to guess, **unguessability must not replace proper access control**.

Associate each view with a stable owner ID and lesson ID.

Keep the underlying ownership records separate from the human-readable URL.

A user must not be able to modify someone else's annotations merely by changing the `view` parameter.

# PART VIII — SHARING PERMISSIONS AND FUTURE PRIVACY

## 25. Future collection visibility modes

**Private | Restricted | Public**

## 2. 🔴 Critical — will break against the live database

### 2.1 The SQL migration is a completely different design from the approved `0012_*` migration

The handoff (§5, §6) locked the schema. The user's new `0012_reading_collections.sql` is not that schema. Concrete deltas:

| Item | Approved design | Your file |
|---|---|---|
| Table DDL | `CREATE TABLE` (fail-loud) | `CREATE TABLE IF NOT EXISTS` (silently skip) |
| Function DDL | `CREATE FUNCTION` (fail-loud) | `CREATE OR REPLACE FUNCTION` |
| Transaction | Explicit `BEGIN;` / `COMMIT;` | None |

### 3.5 Weaker annotation constraints

Approved design (§5.10):
```
highlight → color IS NOT NULL AND color IN (…) AND body = ''
note      → color IS NULL
```

Your file:
```sql
color text check (color is null or color in ('bee','boa','gecko','ladybug','tiger','beetle'))
```

This allows a highlight with no color (rendering will fall back to nothing), and allows a note to carry a colour. The app doesn't currently create such rows, but the DB won't stop a future bug from doing so.

**Fix:** add the two-branch `CHECK` from the spec.

### 3.6 No cleanup trigger — cleanup is application-side only

The spec required an `AFTER DELETE` trigger on `reading_annotations` that removes the corresponding `reading_annotation_links` row when the last annotation is deleted. Your file does this in JS instead:

```js
export async function deleteAnnotation(id,course,lesson){
  …
  if(!left.length){checked(await supabase.from('reading_annotation_links').delete()…);}
}
```

Works in the happy path. Fails if:
- The tab is closed between the two calls.
- The annotation delete succeeds and the link delete errors — the link is orphaned, and `get_shared_reading_lesson` will return `NULL` (because no annotations exist), so the URL becomes dead. Recoverable but not self-healing.

**Fix:** add the trigger. It's two lines of SQL and makes cleanup atomic.

### 3.7 `_random_token()` missing entirely

If you follow 3.4's recommendation to keep UUID tokens, this is moot. If you align with the spec, you need:

```sql
CREATE FUNCTION public._random_token()
RETURNS text LANGUAGE sql VOLATILE SET search_path = ''
AS $$
  SELECT pg_catalog.replace(pg_catalog.replace(
    pg_catalog.rtrim(pg_catalog.encode(extensions.gen_random_bytes(16),'base64'),'='),'+','-'),'/','_');
$$;
```

Plus the `GRANT EXECUTE … TO service_role` and no client role grant.

## 4. 🟡 Other issues

### 4.1 Shared collection requires `?share=<uuid>` — no cross-site sharing story

Since the token is embedded in a query string, sharing `/bookmarks.html?share=abc…` works. But the URL leaks the scheme. ### 4.2 `reading-annotations.js` `owner()` throws for guests, so guests can't view shared annotated lessons

The flow:

```js
try{await owner();owned=true;ownToken=await getAnnotationLink(course,lesson);}catch(e){owned=false;}
```

Fine. But if a guest arrives on `…?annotations=<token>` where the token belongs to someone else, the flow is:

```js
if(urlToken&&urlToken!==ownToken){

  …
  readonly=true; rows=shared.annotations;
}
```

`sharedLesson` calls the `get_shared_reading_lesson` RPC. That RPC is granted to `anon`, so guests can view. ✅ This actually works — just noting it because the `owner()` throw could look alarming.

### 4.3 Notes collection doesn't show counts per lesson

The spec allows either the lesson title alone or a count. You show one row per lesson (correct) but no `N notes` annotation. Minor.

### 4.4 Collections don't display "Created by X" byline to visitors

You show `X · N saved lessons` — reasonable, but the reference demo has `Created by User123 · 4 highlights`. If you want to match the reference more closely, add the word "Created by" to the shared view.

### 4.6 `reading-collections.css` uses `@import url('/assets/fonts/fonts.css')` at the top

`@import` in CSS is render-blocking and should be a `<link>` in the HTML. Since these pages are dynamically built, this is a low-priority note. Not blocking.

### 4.7 `reading-annotations.js` re-registers globals

Each reading page's inline `<script>` defines `window.highlightSelection`, `window.noteSelection`, etc. `reading-annotations.js` doesn't call them (its toolbar has its own handlers), so they're dead code. Clean up by deleting the legacy toolbar HTML and the four `window.*` functions.

### 4.8 `reading-annotations.js` doesn't put a `data-lesson` / `data-course` guard

`lessonFromPath()` returns the course/lesson from the URL path. If `articleContent` isn't present in the DOM (e.g., the DNA HTML malformed close tags moved it into a hidden container), the module bails. Since the DNA malformed `</article></main>` was inside `#selectionToolbar` (which is `display:none`), the `#articleContent` element is still in the correct place earlier in the document — so this actually works. ### 4.9 `offline-export.js` uses `fetch(url)` for lesson HTML — relies on server returning clean HTML

Works on Vercel with rewrite active. On a local `python -m http.server` it works too. On a dev server with auth-gating it could fail. Not blocking.

### 4.10 DNA page shows "Lesson 2 of 2" for the joystick

That's inferred from the number of lessons you have implemented — which is correct given `introduction-to-nucleic-acids` (1) and `dna-location-structure-and-functions` (2) are the only two currently materialised. ### 4.11 `reading-store.js` uses `lessonFromPath` but the DNA HTML injects `data-course` and `data-lesson`

The `data-*` attributes are unused. Not a bug — just dead hint code.

### 4.12 `0012_reading_collections.sql` grants

Your file:
```sql
grant select,insert,update,delete on public.reading_bookmarks,public.reading_annotations,public.reading_annotation_links,public.reading_collection_links to authenticated;
```

Approved design (§5.10, §6.3.G): `reading_annotation_links` must be **`SELECT` only** to `authenticated` — writes go through the lifecycle trigger. Your file grants full CRUD, which means a client could directly insert/update/delete a link row, circumventing the (missing) cleanup trigger. Only matters if you keep the current schema; still, tighten it.

### 4.13 Notes don't render dash underlines when highlight absent

If a user only creates a note (no highlight), the CSS Custom Highlight API still applies `::highlight(vr-notes)`. The dashed underline works. ✅

But if a browser doesn't support CSS Custom Highlight, `render()` bails with a toast and **nothing is rendered**. That's the same behaviour as the reference demo, and it's acceptable — but a fallback would help.

### 4.14 `reading-annotations.css` `.vr-note-asterisk` — asterisk is inserted with `img` inside `<i>`


The `<i>` has class `.ph.ph-asterisk` but no `<i class="ph ph-asterisk"></i>` font stylesheet is loaded on the page. Since the `<img>` is inserted inside, the Phosphor CSS `content: "\fxxx"` on `.ph:before` may still render a duplicate asterisk. Worth checking visually.
